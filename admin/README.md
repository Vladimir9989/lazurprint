# Админ-панель учёта продукции

ТЗ: [`docs/admin-panel.md`](../docs/admin-panel.md). Реализация — этап 1 (см. раздел 12 ТЗ).

## Локальный запуск (Windows, Laragon)

Стек: MySQL из Laragon (`C:\laragon`, поставлен через `winget install LeNgocKhoa.Laragon`)
+ отдельный PHP built-in server (не Apache/Nginx из Laragon — так проще, без настройки vhost).

1. Открыть Laragon, нажать **Start All** (поднимает MySQL, порт 3306, `root` без пароля).
2. Запустить сервер админки:
   ```powershell
   admin/serve.ps1
   ```
   или напрямую:
   ```powershell
   C:\laragon\bin\php\php-8.3.33-Win32-vs16-x64\php.exe -S 127.0.0.1:8000 -t admin/public
   ```
3. Открыть http://127.0.0.1:8000/ — при пустой базе перекинет на `setup.php`,
   там создаётся первый аккаунт (сразу с ролью админа). Дальше — обычная регистрация
   через `register.php` + подтверждение в разделе «Пользователи».

Основной сайт (`npm run dev`, browser-sync) и админка — два независимых процесса,
друг другу не мешают, поднимать нужно оба, если нужно видеть и то, и другое.

БД и пользователь для локальной разработки: `lazur_admin` / `lazur_admin` / `lazur_admin_local`
(создано разово, см. `admin/sql/schema.sql`). Код доступа для регистрации по умолчанию
локально — `lazur2026` (см. `admin/config.local.php`).

## PHP-совместимость

Хостинг — **PHP 7.3** (см. раздел 2 ТЗ), локально стоит PHP 8.3 (из Laragon). Код написан
без 8.x-синтаксиса (без `match`, `??=`, стрелочных функций, типизированных свойств и т.п.),
но перед первой заливкой на сервер всё равно нужно прогнать `php -l` под 7.3 — локально
интерпретатора 7.3 сейчас нет, портативную сборку под линт добавим перед этапом деплоя.

## Структура

- `public/` — единственная папка, которая должна быть web-корнем (веб-сервер отдаёт только
  её). `src/`, `templates/`, `config.local.php`, `sql/` — не публичные, доступ к ним закрыт
  `.htaccess` (на случай, если хостинг всё же смонтирует `admin/` целиком).
- `uploads/` — локальное хранилище фото (вне `public/`). На сервере — вынесено за `www/`
  (см. раздел 2 и 7 ТЗ), путь задаётся в `config.local.php` (`uploads_dir`).

## Публикация новой продукции на сайт

**Важно (актуально с переезда панели на хостинг 2026-09-15, см. «Деплой на боевой
сервер» ниже): Ксюша и Надя работают с панелью на `lazurprint.ru/admin`, у неё своя
прод-база на хостинге — она НЕ совпадает с локальной базой разработчика (`lazur_admin`
в Laragon, см. «Локальный запуск» выше). Поэтому шаги ниже, где Claude «запускает
`admin/tools/*.php`», нужно выполнять так, чтобы команда попала в ПРОД-базу — то есть
через SSH на хостинг, а не локальным `php admin/tools/...` из чекаута на компьютере
разработчика (тот сработает без ошибок, но против пустой/другой локальной базы — молча
ничего не даст ни Ксюше, ни Наде). Для этого в корне репозитория есть готовый скрипт
`admin-remote-exec.js` (тот же SSH-аккаунт `c112136`, креды из `.env`, что и у
`deploy.js`), проверен и подтверждён разработчиком 2026-09-21:
```
node admin-remote-exec.js admin/tools/link-site-image.php <product_id> <site_image_path>
node admin-remote-exec.js admin/tools/mark-site-updated.php <product_id>
```**

**Также важно: шаги, что-то меняющие в проде (снятие флага, привязка фото), выполнять
только ПОСЛЕ реального деплоя на хостинг (`npm run deploy` и, если правилась сама
панель, заливка `admin/`), а не сразу после правки `src/` на компьютере разработчика.
Иначе в панели карточка окажется помечена «опубликовано»/«обновлено», хотя на живом
сайте это ещё не появилось — путаница для Ксюши/Нади, которые ориентируются на статус
в панели.**

Сквозной процесс от готовой карточки в админке до опубликованного товара на сайте:

1. Ксюша/Надя доводят карточку до статуса «Готов к публикации» (фото + название + артикул + цена).
2. Разработчик на главной странице «В работе» нажимает «Экспорт для публикации» — скачивается
   ZIP с оригиналами фото всех таких карточек и `manifest.json` (id/название/категория/артикул/цена
   на каждую).
3. Разработчик просит Claude разместить продукцию на сайте по этому архиву — Claude обрабатывает
   фото (см. `tools/img-tools/` в корне репозитория) и добавляет карточки в
   `src/catalog-suvenir.html`.
4. Разработчик смотрит результат локально, деплоит (`npm run deploy`).
5. Только теперь, когда карточки реально на хостинге: для каждого товара запускается (по
   прод-базе, см. предупреждение выше) `php admin/tools/link-site-image.php <product_id>
   <site_image_path>`, проставляя в базе тот же путь к картинке, что попал на сайт.
6. В админке на вкладке «Что на сайте» — «Обновить список»: парсер разбирает актуальный
   `catalog-suvenir.html` (на хостинге это уже реальный задеплоенный файл), и все карточки,
   чей `site_image_path`+артикул нашлись в свежем разборе, сами помечаются «опубликован» —
   по каждой карточке отдельно ничего нажимать не нужно.

## Обновление данных уже опубликованного товара

Если у уже опубликованного товара поменялись название/артикул/цена (например, Надя правит
их через кнопку «Редактировать» в «Что на сайте» или прямо в карточке), фото пересылать не
нужно — они на сайте уже есть, меняются только данные:

1. Карточка сама помечается флагом «Изменено — обновить на сайте» (см. `needs_site_update`
   в `products`, ставится в `update_product()`).
2. Разработчик на главной странице «В работе» видит кнопку «Экспорт изменений» — скачивается
   ZIP с одним `manifest.json` (id/название/категория/артикул/цена/`site_image_path` каждой
   такой карточки, без фото).
3. Разработчик отдаёт архив Claude — тот находит нужную позицию в `src/catalog-suvenir.html`
   по `site_image_path` (и/или прежнему артикулу из истории карточки), правит
   название/артикул/цену на месте, не трогая фото и разметку.
4. Разработчик смотрит результат локально, деплоит по обычным правилам (`npm run deploy`).
5. Только после реального деплоя — для каждой карточки запускается (по прод-базе, см.
   предупреждение выше) `php admin/tools/mark-site-updated.php <product_id>`, снимая флаг.

## Письма-уведомления

Раздел 8 ТЗ. Своя копия PHPMailer 6.x (namespaced, `PHPMailer\PHPMailer`) лежит в
`admin/vendor/phpmailer/` — не переиспользуем `src/resources/phpmailer/` сайта, потому что
у админки свой отдельный цикл деплоя (см. `CLAUDE.md`), пути на сервере разные. Логика
отправки и подбора адресатов — `admin/src/mail.php`.

Сделаны все события из ТЗ:

| Событие | Кому | Где в коде |
|---|---|---|
| Создана карточка без фото | всем активным `photo` | `create_product()` → `notify_new_product()` |
| Создана карточка без цены/артикула | всем активным `accounting` | там же |
| Карточка стала «Готова к публикации» | админу (`admin_email`) | `check_ready_for_publish()`, вызывается из `update_product()` и `save_product_photo()` |
| Товар опубликован на сайте | автору карточки (`created_by`) | `set_published()` → `notify_published()` |
| Уже опубликованный товар — поменялись название/артикул/цена (например, Надя правит через «Что на сайте») | админу | `update_product()` → `notify_needs_site_update()`, в момент перехода `needs_site_update` 0 → 1 |
| Новая заявка на регистрацию | админу | `register_user()` → `notify_new_registration()` |
| Заявка подтверждена | новому пользователю | `confirm_user()` → `notify_registration_confirmed()` |
| Еженедельная сводка «висит N карточек без движения» | всем активным, кроме `viewer` | Cron → `notify_weekly_digest()`, см. «Cron-задачи» ниже |
| Предупреждение за неделю до автоудаления оригиналов | админу (`admin_email`), одним письмом со списком | Cron → `notify_originals_cleanup_warning()`, см. «Cron-задачи» ниже |

Повторную отправку одного и того же письма по одной и той же карточке предотвращает
`notify_once()` — пишет в `mail_log` и перед отправкой проверяет, не было ли уже такого
письма (тот же адрес + тип события + карточка). Из-за этого «Готово к публикации» уходит
только один раз за жизнь карточки, даже если статус потом откатится и снова станет «ready» —
это осознанное упрощение, отдельный от продукта случай (регистрация) через `notify_once`
не идёт, там дублей и так не бывает.

Письмо «Нужно обновить на сайте» — исключение: оно НЕ через `notify_once`, а через обычный
`send_mail()`, потому что этот флаг может ставиться на одну и ту же карточку много раз за её
жизнь (поставили → разработчик перенёс правки на сайт и снял флаг кнопкой/`mark-site-updated.php`
→ через месяц Надя снова что-то поправила → флаг встал заново) — и каждый такой раз должен
слать новое письмо, а не молчать после первого. Разослать дважды за один и тот же «эпизод»
не даёт сама проверка перехода `needs_site_update` 0 → 1 в `update_product()` — она и без
`mail_log` не вызовет уведомление повторно, пока флаг не будет снят и поднят заново.

**Важно про локальную разработку:** в `config.local.php`/`config.example.php` есть переключатель
`mail_enabled` — локально стоит `false`, письма не уходят по-настоящему (только пишутся в
лог PHP `error_log`), чтобы тестирование фич случайно не слало реальные письма реальным
сотрудникам. На сервере в своём `config.local.php` нужно выставить `true` и заполнить
`smtp_password` (сейчас используется тот же ящик `noreply@info.lazurprint.ru`, что и у формы
на сайте, `mail.netangels.ru:2525`, SSL — реквизиты те же, что в `src/resources/mail.php`).

## Пользователи и восстановление пароля

Экран «Пользователи» (только админ, раздел 12 ТЗ) — заявки на регистрацию с подтверждением
(было раньше) плюс список активных/заблокированных с тремя действиями по каждому:

- **Смена роли** — выпадающий список прямо в строке таблицы, кнопка «Сохранить»
  (`set_user_role()` в `admin/src/auth.php`).
- **Блокировка/разблокировка** — кнопка меняется в зависимости от текущего статуса
  (`set_user_blocked()`). Блокировка сразу же удаляет `remember_tokens` пользователя и
  действует не только при следующем входе, а немедленно: `require_login()`
  (`admin/src/bootstrap.php`) на каждый запрос сверяет статус/роль со свежими данными из
  БД, а не с тем, что закэшировано в сессии при входе — если сотрудника заблокировали, пока
  он работал в панели, его тут же разлогинит и перекинет на `login.php?blocked=1`. Смена роли
  подхватывается так же на лету (например, если у admin отобрали роль — он теряет доступ к
  «Пользователям» сразу, без повторного входа).
- **Сбросить пароль** — админ может выслать сотруднику ссылку для смены пароля, не зная его
  текущий пароль (та же механика, что у формы «Забыли пароль» — см. ниже).

Защита от самоблокировки: нельзя сменить роль или заблокировать самого себя (строка со своим
аккаунтом показывает данные текстом, без органов управления), и нельзя заблокировать или
понизить в роли **последнего активного админа** — `set_user_role()`/`set_user_blocked()`
считают активных админов и отказывают с понятной ошибкой, если действие оставило бы систему
без единого администратора.

**Восстановление пароля** (раздел 12 ТЗ, было «до этого — админ сбрасывает руками»):
`forgot-password.php` — форма «почта → письмо со ссылкой», не показывает, зарегистрирована ли
эта почта (одинаковый ответ в любом случае, чтобы нельзя было перебором проверять список
сотрудников). `reset-password.php` — форма нового пароля по ссылке из письма. Ссылка живёт
`PASSWORD_RESET_TTL_MINUTES` (60 минут, `admin/src/auth.php`), одноразовая, при повторном
запросе новая ссылка аннулирует все прежние неиспользованные для этого пользователя. Токен —
та же схема селектор/валидатор, что у cookie «запомнить меня» (`password_resets`, отдельная
таблица в `admin/sql/schema.sql`). Успешный сброс пароля также разлогинивает все «запомненные»
устройства пользователя (`remember_tokens`) — если пароль меняли из-за утечки, старые сессии
не должны продолжать молча работать.

Проверено локально: смена роли, блокировка/разблокировка, обе защитные проверки (нельзя
самого себя, нельзя последнего админа) — через прямой вызов функций в транзакции с откатом
(синтетические тестовые пользователи, реальные данные не затронуты). Полный цикл восстановления
пароля и мгновенное действие блокировки — вживую через HTTP на одном временном тестовом
пользователе (создан и полностью удалён после проверки): запрос ссылки → переход по ней →
смена пароля → старый пароль перестал подходить, новый сработал; блокировка админом во время
активной сессии оборвала доступ на следующем же запросе, без повторного входа.

## Cron-задачи

Раздел 7 (п.2) и 12 ТЗ. Хостинг NetAngels даёт вкладку Cron (запуск команды по расписанию),
поэтому это три отдельных CLI-скрипта в `admin/tools/` — не веб-страницы, доступа по HTTP
не имеют. На сервере в панели Cron прописать команды вида `php /home/c112136/.../admin/tools/<script>.php`
на нужном расписании; вывод в stdout/stderr — для лога хостинга, само по себе ни на что не влияет.

| Скрипт | Расписание | Что делает |
|---|---|---|
| `cron-nightly-sync.php` | раз в сутки, ночью | То же, что кнопка «Обновить список» на «Что на сайте»: `resync_site_catalog()` + `auto_publish_after_sync()` — пересобирает снимок каталога и автоматически отмечает найденные там карточки опубликованными. |
| `cron-weekly-digest.php` | раз в неделю | `notify_weekly_digest()` — всем активным, кроме `viewer`, письмо со списком карточек без движения дольше `stale_product_days` дней (по умолчанию 14; не архивные и ещё не в финальном состоянии «опубликован без правок»). Это периодический срез, не разовое событие — уходит заново при каждом запуске, а не один раз через `notify_once`. |
| `cron-cleanup-originals.php` | раз в неделю | Автоудаление оригиналов (то же действие, что ручная кнопка «Удалить оригиналы») у карточек, опубликованных больше `originals_auto_delete_days` дней назад (по умолчанию 45). Плюс одно письмо-предупреждение админу со списком карточек, которым до удаления осталось меньше `originals_warning_days_before` дней (по умолчанию 7) — дедуп на карточку через `mail_log`, чтобы не предупреждать о той же карточке дважды. |

Все три настройки (`stale_product_days`, `originals_auto_delete_days`,
`originals_warning_days_before`) — в `config.local.php`/`config.example.php`, менять можно
без правки кода. Системный «пользователь» для истории карточки (`product_events.user_id`) —
`NULL`, колонка это допускает; по аналогии с `admin/tools/link-site-image.php` и
`mark-site-updated.php`, у которых тот же приём.

Проверено локально прогоном всех трёх скриптов через CLI на синтетических тестовых карточках
(в реальной базе не остались): сверка каталога отрабатывает без ошибок, сводка находит только
карточки без движения дольше порога, предупреждение и автоудаление срабатывают на нужных сроках
и не задваиваются при повторном запуске (предупреждение — через `mail_log`, удаление — само
по себе идемпотентно за счёт `originals_deleted_at`), а еженедельная сводка, наоборот, корректно
уходит заново на каждый запуск.

## Деплой на боевой сервер

Пошаговая инструкция для пользователя (не разработчика) — переезд панели на NetAngels.
Актуально с 2026-09-15, когда вся функциональность панели (раздел 12 ТЗ, этапы 1–3)
проверена локально.

Панель — это не статика и не часть `npm run deploy` сайта, заливается и настраивается
отдельно, своими шагами.

### 0. Что понадобится

- Доступ на `panel.netangels.ru` (тот же аккаунт, что для сайта).
- Программа для захода по SFTP на хостинг — например **FileZilla** или **WinSCP**
  (бесплатные, если ещё не стоят — скачать с официальных сайтов). Логин/пароль — тот же
  SSH-аккаунт `c112136`, что уже используется для заливки сайта (см. `CLAUDE.md`, раздел
  «Деплой» — спросить у разработчика реальный пароль, если его нет под рукой).

### 1. Куда заливать файлы `admin/`

Через FileZilla/WinSCP зайти по SFTP под `c112136`. Домашняя папка после входа —
`/home/c112136`. Дальше:

1. Зайти в `lazurprint.ru/www/`.
2. Создать там папку `admin` (если разработчик не создал заранее) и залить в неё **всё
   содержимое** локальной папки `admin/` из проекта — `public/`, `src/`, `templates/`,
   `sql/`, `tools/`, `uploads/` (пустую), `vendor/`, `.htaccess`, `index.php` — то есть
   один в один, как оно лежит в репозитории. Файл `config.local.php` заливается отдельно,
   после того как он будет заполнен настоящими данными (шаг 4) — заранее не заливать пустой
   или локальный.

   Получится путь `/home/c112136/lazurprint.ru/www/admin/...` — то есть `admin/` становится
   подпапкой того же сайта, что и вся остальная статика.
3. Отдельно, **рядом с `www`, а не внутри неё**, создать папку для фото:
   `/home/c112136/lazurprint.ru/uploads` (пустая папка). Так требует ТЗ — исходники фото не
   должны лежать в общедоступной через браузер папке сайта.

Не пугайтесь, что все служебные папки (`src`, `templates`, `sql`, `tools`, `vendor`,
`config.local.php`) окажутся физически внутри `www/admin/` — в каждой из них уже лежит
файл `.htaccess`, который запрещает открыть эти файлы напрямую по ссылке в браузере. Снаружи
через браузер будет виден только `public/` (плюс маленький `admin/index.php`, который просто
перебрасывает с адреса `lazurprint.ru/admin/` на `lazurprint.ru/admin/public/`).

### 2. Создать базу данных MySQL

В панели `panel.netangels.ru` найти раздел **«Базы данных» / «MySQL»** (обычно рядом с тем
же контейнером, где смотрели SSH/FTP-доступ):

1. Создать новую базу — например, назвать `c112136_lazur_admin` (NetAngels обычно сам
   добавляет префикс аккаунта к имени, ориентируйтесь на то, что покажет форма).
2. Создать пользователя MySQL для этой базы с полным доступом к ней, задать пароль (сохранить
   его — он понадобится на шаге 4). Если хостинг предлагает совместить создание базы и
   пользователя одной формой — воспользоваться этим.
3. Открыть **phpMyAdmin** для этой базы (обычно кнопка/ссылка рядом с базой в том же
   разделе панели).
4. В phpMyAdmin выбрать созданную базу → вкладка **«Импорт» / «SQL»** → загрузить файл
   `admin/sql/schema.sql` из проекта (он маленький, 152 строки, загрузится мгновенно) →
   выполнить. Должны появиться таблицы `users`, `products`, `product_events`,
   `remember_tokens`, `password_resets`, `mail_log` и другие — если в phpMyAdmin слева
   в списке таблиц появилось десяток с лишним пунктов, всё прошло успешно.

### 4. Проверить версию PHP

В панели NetAngels в настройках сайта/контейнера проверить, что для папки `admin/` (или для

другое — переключить на 7.3.

### 5. Настроить Cron

В панели NetAngels найти вкладку **«Cron»** у контейнера/сайта. Добавить три задачи (обычно
форма просит «команда» + «расписание»):

| Команда | Расписание |
|---|---|
| `php /home/c112136/lazurprint.ru/www/admin/tools/cron-nightly-sync.php` | раз в сутки, ночью (например, 03:00) |
| `php /home/c112136/lazurprint.ru/www/admin/tools/cron-weekly-digest.php` | раз в неделю (например, понедельник 09:00) |
| `php /home/c112136/lazurprint.ru/www/admin/tools/cron-cleanup-originals.php` | раз в неделю (можно в то же время, что и сводку, или рядом) |

Если форма Cron на NetAngels просит путь к PHP явно (не просто `php`) — использовать тот же
путь к интерпретатору PHP 7.3, что показывает панель для этого сайта (обычно что-то вроде
`/usr/bin/php` или `/opt/php7.3/bin/php` — конкретный путь подскажет сама форма/подсказка в
панели при добавлении задачи).

1. Открыть `https://lazurprint.ru/admin/` в браузере — должно перекинуть на страницу входа

4. Проверить письма: например, кнопка «Сбросить пароль» в «Пользователях» или создание
   карточки без фото — почта должна реально прийти (не просто попасть в лог, как локально) —
   значит, `mail_enabled`/`smtp_password` настроены верно.
5. Удалить тестовую карточку и тестового пользователя, если не нужны.
6. Кнопка «Вход для сотрудников» в подвале сайта (`lazurprint.ru`) должна вести на рабочую

Если что-то не открывается или выдаёт ошибку — прислать текст ошибки (или скриншот)
разработчику, дальше разбираться вместе.
