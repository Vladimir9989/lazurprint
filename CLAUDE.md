# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

Статический многостраничный сайт типографии «Лазурь» (lazurprint.ru). Сборка на **Gulp 4**: SCSS → CSS, ES-модули → бандл, HTML-партиалы → страницы. Серверной логики, кроме PHP-обработчика формы (`mail.php` + PHPMailer), нет.

## Команды

```bash
npm run dev      # gulp dev  — чистит dist/build, собирает, поднимает browser-sync (baseDir: dist) и watch
npm run build    # gulp build — продакшен-сборка (минификация HTML/CSS/JS, sitemap.xml)
```

Отдельные таски можно запускать точечно: `npx gulp styles`, `npx gulp scripts`, `npx gulp htmlMinify`, `npx gulp sitemap`.

> **НЕ запускай `npm run dev` / `npm run build` «на проверку».** У пользователя обычно уже поднят свой dev-сервер с watch — он сам пересобирает `dist/` и обновляет браузер при любой правке в `src/`, отдельная пересборка не нужна и ничего не «проверяет». Хуже того: `gulp dev`/`gulp build` начинаются с `clean` (`del(['dist','build'])`). Если запустить сборку, пока живёт пользовательский dev, `clean` сотрёт `dist` на ходу и начнёт гонку с работающим watch — сборка успевает разложить HTML/CSS/JS, но не докопировать картинки (их 2400+ плюс тяжёлые видео), и страница остаётся с битым логотипом/иконками. Именно так однажды и сломалось. Если нужно только убедиться, что SCSS/JS компилируется без ошибок — запускай узкий таск (`npx gulp styles`), а не полный dev/build (учти, он всё равно пишет в `dist`/`build`). И не поднимай собственные статические серверы для предпросмотра — пользователь смотрит свой browser-sync.

```bash
npm run deploy   # gulp build, затем заливка build/ на хостинг NetAngels (deploy.js)
```

Деплой настроен через `deploy.js`, поддерживает и SFTP (`ssh2-sftp-client`), и FTP (`basic-ftp`) — переключатель `DEPLOY_PROTOCOL` в `.env` (`sftp` | `ftp`). **По умолчанию сейчас `sftp`** — он стабильно дотягивает большие файлы (FTP на видео >~30 МБ таймаутил по control-socket и подвешивал деплой), а с `fastPut` (параллельные чанки) ещё и заметно быстрее обычного `put` (на этом хостинге ~3.5×: 43 МБ за ~105 c против ~374 c). Креды берутся из `.env` (см. `.env.example`). Есть два набора переменных: общие `DEPLOY_*` (используются при ftp) и `DEPLOY_SFTP_*` (при sftp берутся вместо общих, если заданы) — так обе настройки живут в `.env` рядом и переключение между протоколами — это только смена `DEPLOY_PROTOCOL`, без переписывания логина/пароля/пути. `.env` в `.gitignore` — реальные пароли никогда не коммитятся, только пустой шаблон `.env.example`.

На NetAngels у контейнера два независимых набора кредов (`panel.netangels.ru/hosting/` → контейнер → вкладка «доступ SSH/FTP»):
- общий **SSH-логин** контейнера (у нас `c112136`) — доступ по SFTP ко всему контейнеру (всем сайтам). Домашняя папка — `/home/c112136`, а корень сайта — **`/home/c112136/lazurprint.ru/www`** (это и есть `DEPLOY_SFTP_REMOTE_DIR`, у SSH это НЕ `/www`). Именно этот вариант сейчас используется по умолчанию (`DEPLOY_PROTOCOL=sftp`).
- отдельные **FTP-аккаунты** на каждый сайт (вида `cXXXXXX_domain_ru`), у lazurprint.ru — `c112136_lazurprint_ru`, root которого сразу `/www`. Привязан только к этому сайту; остаётся как резервный вариант (`DEPLOY_PROTOCOL=ftp`, `DEPLOY_REMOTE_DIR=/www`).

Очень крупные видео (> `DEPLOY_MAX_SIZE_MB`, по умолчанию 50 МБ) деплой пропускает по размеру и печатает списком в начале — их заливают **вручную** через файловый менеджер (три ролика в `images/img/events/` по 120–340 МБ; по SFTP они бы залились, но это 10–15 мин каждый, а меняются раз в год). Средние видео (~30–45 МБ) через SFTP заливаются штатно и в ручной заливке больше не нуждаются. Есть ещё набор `manualSkip` в `deploy.js` (сейчас пустой) — точка расширения: если какой-то конкретный файл будет упорно рвать заливку, впиши его путь (относительно `build/`, через `/`) туда, и деплой будет его всегда пропускать.

Скрипт только заливает файлы (upload), ничего не удаляет на сервере. Инкрементальность: после успешной заливки каждого файла его путь/размер/**sha256-хеш содержимого** сразу пишутся в `.deploy-manifest.json` (в `.gitignore`, не коммитится). В следующий запуск заливаются только новые файлы или те, у кого изменился размер/хеш. Манифест обновляется построчно по ходу дела, а не в конце — если соединение оборвётся (FTP на больших объёмах нестабилен), повторный `npm run deploy` продолжит с места обрыва, а не полезет заливать всё заново. При обрыве посреди файла скрипт сам переподключается и повторяет именно этот файл (до 4 попыток). Чтобы гарантированно перезалить всё с нуля — удалить `.deploy-manifest.json`.

Сравнение именно по **хешу**, не по mtime: gulp при каждой пересборке переписывает вообще все файлы в `dist`/`build` (даже если их содержимое не менялось) — если бы деплой сверялся по mtime, любая мелкая правка (например, одна новость) заново заливала бы весь `build/` (~2800 файлов, ~2 ГБ, десятки минут по FTP). При сверке по хешу реально перезаливаются только файлы, которые правда изменились — обычно секунды/пара минут. Дополнительно, чтобы HTML-страницы не «менялись» на пустом месте при каждой сборке: `gulp-version-number` (таск `htmlMinify`) берёт версию не из даты/времени (`%DT%`), а из `package.json` (`pkg.version`) — она одна и та же во всех сборках, пока её не поменять руками. **Если правишь `main.css`/`app.js` и нужно сбросить кэш браузера у клиентов — вручную бампни `version` в `package.json`** (иначе `?_v=...` в HTML не изменится и старый закэшированный css/js может отдаваться из кеша браузера).

Тестов и линтеров в проекте нет.

Разница `dev` vs `build`: флаг `prod` (см. таск `isProd`) включает sourcemaps только в dev, а минификацию (`cleanCSS`, `uglify`, `htmlMin`) и генерацию `sitemap.xml` — только в build. Оба режима пишут результат **одновременно в `dist/` и `build/`**.

## Архитектура сборки (gulpfile.js)

Ключевая особенность — **два независимых конвейера JavaScript**, их легко перепутать:

1. **Бандл `app.js`** (таск `scripts`): собирается из `src/js/components/**/*.js` + `src/js/main.js`, прогоняется через Babel и concat в `app.js`. `main.js` — общая логика всех страниц (бургер-меню, выпадающие списки хедера, анимации появления по скроллу через классы `.fade-in`/`.slide-in-*`/`.scale-in` + `.visible`).

2. **Файлы из `src/resources/`** (таск `resources`): копируются **как есть, без обработки** в корень `dist`/`build`. Здесь лежат:
   - постраничные скрипты (`index.js`, `catalog.js`, `events.js`, `about.js`, `cart.js`, `map.js`, …) — подключаются вручную через `<script>` на нужных страницах;
   - сторонние библиотеки (`swiper-bundle.min.js`, `choices.min.js`, `just-validate.min.js`, `inputmask.min.js`, `lazyload.min.js`, `rellax.min.js`, `simplebar.min.js`);
   - PHP бэкенд формы (`mail.php`, `recaptchalib.php`, `phpmailer/`);
   - `robots.txt`, `sitemap.xml`.

   Новый JS, который должен попасть в бандл и пройти Babel, кладётся в `src/js/`. Скрипт конкретной страницы (или внешняя либа) — в `src/resources/` и подключается тегом `<script>` в HTML.

CSS: все партиалы `src/styles/_*.scss` импортируются в `src/styles/styles.scss`, который через таск `styles` собирается в единый `main.css`. При добавлении нового `_*.scss` обязательно добавить `@import` в `styles.scss` — иначе он не попадёт в сборку.

HTML: страницы лежат в `src/*.html`, переиспользуемые блоки — в `src/html/*.html` (header, footer, consultation, reviews, steps и т.д.) и вставляются через **gulp-file-include** синтаксисом `@@include('html/header.html', {})`. Менять шапку/подвал нужно в `src/html/`, а не в каждой странице.

Версионирование: `gulp-version-number` дописывает `?_v=...` к ссылкам на css/js в HTML для сброса кэша (пишет `src/version.json`). Значение версии — `pkg.version` из `package.json`, не дата/время: стабильно между сборками, меняется только при ручном бампе версии в `package.json` (см. раздел про деплой — это важно и для скорости инкрементального деплоя).

Шрифты: `.ttf` из `src/fonts/` конвертируются в `.woff` и `.woff2`.
Изображения: png/jpg/jpeg/svg копируются таском `images`; webp/mp4/mov/ico/pdf — таском `imagesCopy`; svg из `src/images/svg/` собираются в `sprite.svg` (svg-sprite).

## Контент-страницы

`src/articles*.html` (~100 файлов) и `src/news*.html` — статьи блога и новости, по сути контент-шаблоны с одинаковой структурой. Каталог сувениров оперирует данными из `src/js/data/products.json` (поля: `category`, `name`, `price`, `article`, `image`).

## Дизайн и стилистика

Сайт оформлен в **светлом корпоративном стиле** на синем бренде. Палитра и брейкпоинты — в `src/styles/_variables.scss`.

- Основные цвета: `--color-primary` `#3E77FB` (фирменный синий), акцент `#6de2eb` (циан), заголовки — `--color-galaxy` `#081f5c` (тёмно-синий), текст — `#333`/`--color-dim-gray`. Градиент-акцент `linear-gradient(135deg, #3E77FB, #6de2eb)` используется в заголовках секций и подчёркиваниях.
- Хедер (`_header.scss`) — белый, футер (`_footer.scss`) — светло-голубой; оба импортируются на все страницы. Главная (`_hero`, `_work`, `_counter`, `_steps`, `_benefit`, `_contacts`) — светлые секции.
- **Логотип — две версии, не перепутать:** `logo_Lazur.svg` со слоганом в белом цвете — только под **тёмный** фон; `logo_Lazur_01.png` (синий) — под **светлый** фон. На светлых хедере/футере используется PNG.

## Важное

- `dist/` и `build/` — артефакты сборки, в `.gitignore`. Никогда не редактировать их напрямую — правки делаются в `src/` и пересобираются.
- `.env` содержит `GOOGLE_CLOUD_PROJECT` (не используется самой gulp-сборкой).

## Самообновление этого файла

Если в ходе работы появляется изменение, важное для понимания сборки или архитектуры проекта (новый таск в gulpfile, новый JS-конвейер, новая SCSS-подсистема, изменение конвенций именования, новая корневая зависимость и т.п.) — дописывай его сюда самостоятельно, без отдельного запроса.

Не нужно фиксировать здесь: обычные статьи/страницы контента (`articles*.html`, `news*.html` уже описаны обобщённо в разделе «Контент-страницы»), точечные правки вёрстки и стилей конкретной страницы, разовые правки текста — то есть всё, что не меняет общие правила сборки или архитектуры, которым должен следовать любой, кто работает с этим репозиторием.
