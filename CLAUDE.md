# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

Статический многостраничный сайт типографии «Лазурь» (lazurprint.ru). Сборка на **Gulp 4**: SCSS → CSS, ES-модули → бандл, HTML-партиалы → страницы. Серверной логики, кроме PHP-обработчика формы (`mail.php` + PHPMailer), нет.

## Команды

```bash
npm run dev      # gulp dev  — чистит dist/build, собирает, поднимает browser-sync (baseDir: dist) и watch
npm run build    # gulp build — продакшен-сборка (минификация HTML/CSS/JS, sitemap.xml)
```

Отдельные таски можно запускать точечно: `npx gulp styles`, `npx gulp scripts`, `npx gulp htmlMinify`, `npx gulp sitemap`.

> **НЕ запускай `npm run dev` / `npm run build` «на проверку».** У пользователя обычно уже поднят свой dev-сервер с watch — он сам пересобирает `dist/` и обновляет браузер при любой правке в `src/`, отдельная пересборка не нужна и ничего не «проверяет». Хуже того: `gulp dev`/`gulp build` начинаются с `clean` (`del(['dist','build'])`). Если запустить сборку, пока живёт пользовательский dev, `clean` сотрёт `dist` на ходу и начнёт гонку с работающим watch — сборка успевает разложить HTML/CSS/JS, но не докопировать картинки (их 2400+ плюс тяжёлые видео), и страница остаётся с битым логотипом/иконками. Именно так однажды и сломалось. Если нужно только убедиться, что SCSS/JS компилируется без ошибок — запускай узкий таск (`npx gulp styles`), а не полный dev/build (учти, он всё равно пишет в `dist`/`build`). И не поднимай собственные статические серверы для предпросмотра — пользователь смотрит свой browser-sync.

```bash
npm run deploy   # gulp build, затем заливка build/ на хостинг NetAngels (deploy.js)
```

Деплой настроен через `deploy.js`, поддерживает и SFTP (`ssh2-sftp-client`), и FTP (`basic-ftp`) — переключатель `DEPLOY_PROTOCOL` в `.env` (`sftp` | `ftp`). **По умолчанию сейчас `sftp`** — он стабильно дотягивает большие файлы (FTP на видео >~30 МБ таймаутил по control-socket и подвешивал деплой), а с `fastPut` (параллельные чанки) ещё и заметно быстрее обычного `put` (на этом хостинге ~3.5×: 43 МБ за ~105 c против ~374 c). Креды берутся из `.env` (см. `.env.example`). Есть два набора переменных: общие `DEPLOY_*` (используются при ftp) и `DEPLOY_SFTP_*` (при sftp берутся вместо общих, если заданы) — так обе настройки живут в `.env` рядом и переключение между протоколами — это только смена `DEPLOY_PROTOCOL`, без переписывания логина/пароля/пути. `.env` в `.gitignore` — реальные пароли никогда не коммитятся, только пустой шаблон `.env.example`.

На NetAngels у контейнера два независимых набора кредов (`panel.netangels.ru/hosting/` → контейнер → вкладка «доступ SSH/FTP»):
- общий **SSH-логин** контейнера (у нас `c112136`) — доступ по SFTP ко всему контейнеру (всем сайтам). Домашняя папка — `/home/c112136`, а корень сайта — **`/home/c112136/lazurprint.ru/www`** (это и есть `DEPLOY_SFTP_REMOTE_DIR`, у SSH это НЕ `/www`). Именно этот вариант сейчас используется по умолчанию (`DEPLOY_PROTOCOL=sftp`).
- отдельные **FTP-аккаунты** на каждый сайт (вида `cXXXXXX_domain_ru`), у lazurprint.ru — `c112136_lazurprint_ru`, root которого сразу `/www`. Привязан только к этому сайту; остаётся как резервный вариант (`DEPLOY_PROTOCOL=ftp`, `DEPLOY_REMOTE_DIR=/www`).

Очень крупные видео (> `DEPLOY_MAX_SIZE_MB`, по умолчанию 50 МБ) деплой пропускает по размеру и печатает списком в начале — их заливают **вручную** через файловый менеджер (три ролика в `images/img/events/` по 120–340 МБ; по SFTP они бы залились, но это 10–15 мин каждый, а меняются раз в год). Средние видео (~30–45 МБ) через SFTP заливаются штатно и в ручной заливке больше не нуждаются. Есть ещё набор `manualSkip` в `deploy.js` (сейчас пустой) — точка расширения: если какой-то конкретный файл будет упорно рвать заливку, впиши его путь (относительно `build/`, через `/`) туда, и деплой будет его всегда пропускать.

Скрипт только заливает файлы (upload), ничего не удаляет на сервере. Инкрементальность: после успешной заливки каждого файла его путь/размер/**sha256-хеш содержимого** сразу пишутся в `.deploy-manifest.json` (в `.gitignore`, не коммитится). В следующий запуск заливаются только новые файлы или те, у кого изменился размер/хеш. Манифест обновляется построчно по ходу дела, а не в конце — если соединение оборвётся (FTP на больших объёмах нестабилен), повторный `npm run deploy` продолжит с места обрыва, а не полезет заливать всё заново. При обрыве посреди файла скрипт сам переподключается и повторяет именно этот файл (до 4 попыток). Чтобы гарантированно перезалить всё с нуля — удалить `.deploy-manifest.json`.

Сравнение именно по **хешу**, не по mtime: gulp при каждой пересборке переписывает вообще все файлы в `dist`/`build` (даже если их содержимое не менялось) — если бы деплой сверялся по mtime, любая мелкая правка (например, одна новость) заново заливала бы весь `build/` (~2800 файлов, ~2 ГБ, десятки минут по FTP). При сверке по хешу реально перезаливаются только файлы, которые правда изменились — обычно секунды/пара минут. Дополнительно, чтобы HTML-страницы не «менялись» на пустом месте при каждой сборке: `gulp-version-number` (таск `htmlMinify`) берёт версию не из даты/времени (`%DT%`), а из `package.json` (`pkg.version`) — она одна и та же во всех сборках, пока её не поменять руками. **Если правишь `main.css`/`app.js` и нужно сбросить кэш браузера у клиентов — вручную бампни `version` в `package.json`** (иначе `?_v=...` в HTML не изменится и старый закэшированный css/js может отдаваться из кеша браузера).

Тестов и линтеров в проекте нет.

Разница `dev` vs `build`: флаг `prod` (см. таск `isProd`) включает sourcemaps только в dev, а минификацию (`cleanCSS`, `uglify`, `htmlMin`) и генерацию `sitemap.xml` — только в build. Оба режима пишут результат **одновременно в `dist/` и `build/`**.

## Архитектура сборки (gulpfile.js)

Ключевая особенность — **два независимых конвейера JavaScript**, их легко перепутать:

1. **Бандл `app.js`** (таск `scripts`): собирается из `src/js/components/**/*.js` + `src/js/main.js`, прогоняется через Babel и concat в `app.js`. `main.js` — общая логика всех страниц (бургер-меню, выпадающие списки хедера, анимации появления по скроллу через классы `.fade-in`/`.slide-in-*`/`.scale-in` + `.visible`).

2. **Файлы из `src/resources/`** (таск `resources`): копируются **как есть, без обработки** в корень `dist`/`build`. Здесь лежат:
   - постраничные скрипты (`index.js`, `catalog.js`, `events.js`, `about.js`, `cart.js`, `map.js`, …) — подключаются вручную через `<script>` на нужных страницах;
   - сторонние библиотеки (`swiper-bundle.min.js`, `choices.min.js`, `just-validate.min.js`, `inputmask.min.js`, `lazyload.min.js`, `rellax.min.js`, `simplebar.min.js`);
   - PHP бэкенд формы (`mail.php`, `recaptchalib.php`, `phpmailer/`);
   - `robots.txt`, `sitemap.xml`.

   Новый JS, который должен попасть в бандл и пройти Babel, кладётся в `src/js/`. Скрипт конкретной страницы (или внешняя либа) — в `src/resources/` и подключается тегом `<script>` в HTML.

CSS: все партиалы `src/styles/_*.scss` импортируются в `src/styles/styles.scss`, который через таск `styles` собирается в единый `main.css`. При добавлении нового `_*.scss` обязательно добавить `@import` в `styles.scss` — иначе он не попадёт в сборку. Индивидуальные стили конкретных статей/новостей (см. раздел «Индивидуальное оформление статей и новостей») лежат отдельно, в подпапке `src/styles/articles/`, а не плоским списком рядом с остальными партиалами — путь импорта тогда `@import 'articles/имя-файла';`. Партиалы Sass компилирует по имени файла (файлы с `_` в начале — partial, в отдельный CSS не превращаются), так что вложенность в подпапки на сборку не влияет, только на организацию.

HTML: страницы лежат в `src/*.html`, переиспользуемые блоки — в `src/html/*.html` (header, footer, consultation, reviews, steps и т.д.) и вставляются через **gulp-file-include** синтаксисом `@@include('html/header.html', {})`. Менять шапку/подвал нужно в `src/html/`, а не в каждой странице.

Версионирование: `gulp-version-number` дописывает `?_v=...` к ссылкам на css/js в HTML для сброса кэша (пишет `src/version.json`). Значение версии — `pkg.version` из `package.json`, не дата/время: стабильно между сборками, меняется только при ручном бампе версии в `package.json` (см. раздел про деплой — это важно и для скорости инкрементального деплоя).

Шрифты: `.ttf` из `src/fonts/` конвертируются в `.woff` и `.woff2`.
Изображения: png/jpg/jpeg/svg копируются таском `images`; webp/mp4/mov/ico/pdf — таском `imagesCopy`; svg из `src/images/svg/` собираются в `sprite.svg` (svg-sprite).

## Контент-страницы

`src/articles*.html` (~100 файлов) и `src/news*.html` — статьи блога и новости, по сути контент-шаблоны с одинаковой структурой.

`src/js/data/products.json` (поля: `category`, `name`, `price`, `article`, `image`) — **не используется сборкой и рантаймом**: ни один JS-файл его не импортирует и нефетчит (проверено аудитом 2026-09-03). Реальный каталог сувениров (`catalog-suvenir.html`) — это статичная вёрстка, карточки товаров (`<li class="catalog__item catalog-item">`) прописаны прямо в HTML вручную (см. раздел «Добавление новой продукции в каталог» — шаг 8 про вставку карточки в HTML). Файл, похоже, орфанный (данные к тому же протухли — часть `image`-путей ссылается на кириллические папки `rs/Магниты/`, `rs/Чай/` и т.п., которых не существует, товар лежит в транслитерированных `rs/Magnity/`, `rs/Chay/`). Прежде чем что-то менять на основе этого файла — свериться, действительно ли он используется на момент чтения.

## Индивидуальное оформление статей и новостей

Подтверждённое предпочтение пользователя: **каждая новая статья или новость, которую мы создаём (не рядовая правка текста в существующей, а новый материал), получает собственное уникальное визуальное оформление**, а не типовую вёрстку общих `.news`/`.card` стилей, которой обходятся рядовые статьи из ~100 файлов `articles*.html`. Пример и точка отсчёта — `articles111.html` (календари), `articles112.html` (открытки), `news48.html` (запуск конструктора футболок lazur-wear.ru) и `articles113.html` (продукция для выставок).

Как это устроено технически:
- Стили каждого такого материала — отдельный SCSS-partial в **`src/styles/articles/`** (папка заведена 2026-07-28 специально под это, а не как раньше — плоским списком вперемешку с остальными партиалами styles.scss), импортируется в `styles.scss` через `@import 'articles/имя-файла';`. По одному файлу на статью/новость.
- У каждого материала — **свой уникальный CSS-префикс классов**, чтобы стили разных статей не пересекались друг с другом: `.cal-` (`articles111.html`, `articles112.html` — общий префикс, открытки доп. используют `.cal-taxonomy`/`.cal-gallery` поверх базы календарей), `.news-feature` (`news48.html`), `.expo-` (`articles113.html`). Для новой статьи — придумывать новый префикс, не переиспользовать чужой.
- **Не повторять цветовую палитру уже использованных материалов** — у каждой статьи/новости должен быть свой акцент, отличимый от соседних на странице `articles.html`/`news.html`: `.cal-` — синий/циан (в тон бренда), `.news-feature` — сиреневый/бирюзовый, `.expo-` — терракотовый/янтарный. Следующей — брать любой ещё не занятый сочетание, а не третий оттенок синего.
- Референс по уровню исполнения (не для копирования 1:1) — то, что уже сделано в этих файлах: hero-блок с фоновыми «блобами»-пятнами и градиентом, чип-навигация по разделам статьи (`data-spy`/якоря), карточки/сетки с кастомными inline-SVG иконками, таймлайны, врезки-цитаты. Оформление должно быть современным и аккуратным, но не обязано повторять именно эти компоненты — состав секций подбирается под контент конкретной статьи.
- Если под материал ещё нет готовых фото — не оставлять `<img>` на несуществующий файл (будет битая иконка): либо CSS-плейсхолдер (пунктирная рамка + подпись, что должно быть на фото — так делали для `articles113.html` до того, как пользователь прислал сгенерированные ИИ-иллюстрации), либо существующий общий `images/img/articles/file.jpg` для карточки в списке. Для самих иллюстраций статьи полезно сразу писать промпты для генерации в нейросети (см. пример в истории `articles113.html`) — пользователь генерирует и присылает картинки, они подставляются на место плейсхолдеров.
- Это не касается рядовых статей (`articles1.html`…`articles110.html` и большинство `newsNN.html`) — у них типовая вёрстка и отдельный стиль заводить не нужно, правило только для новых материалов, которые создаются сейчас и далее.

## Обработка фото (tools/img-tools)

Для пакетной обработки фото товаров (обрезка/ресайз/баланс белого) есть отдельный Node-инструментарий на **sharp** в `tools/img-tools/` (своя `package.json`, зависимости ставятся отдельно от корневых через `npm install` внутри этой папки). Не путать с gulp-таском `images` — это офлайн-утилиты, которые готовят фото до того, как они попадут в `src/images/`.

- `resize-catalog.js <srcDir> <outDir> [--rot90/180/270 файлы]` — автообрезка карточки товара по насыщенности (отделяет товар от серого/белого фона), приведение к квадрату с полем, баланс белого по углам кадра, ресайз 300×300 JPG. Опции `--rot*` — повернуть конкретные файлы (для кадров, снятых на бок). Ловушка: если в кадре у самого края (обычно снизу) виден цветной калибровочный штрих/шкала фотографа — детектор насыщенности может принять его за товар и растянуть bbox до края кадра (итог — товар мелкий и смещённый, а не по центру). Проверять по логу `crop NNNpx`: если у одного файла из партии сторона кроп-квадрата заметно больше остальных — смотреть, что попало в кадр по краям, и при необходимости обрезать лишнее (`sharp().extract()`) до прогона через скрипт.
- `magnity-rezh.js <srcDir> <outDir> [--preview grid.png]` — вариант для горизонтальных товаров (например, магнитов): плотная обрезка по объекту + вписывание contain'ом в квадрат на фоне карточки `#f8f8f8`, а не квадратная обрезка вокруг товара.
- `montage.js <dir> <outFile.png> [cols]` — собирает все картинки из папки в один контактный лист (сетка с подписями-именами файлов) для быстрой визуальной проверки результата.
- `flatten-bg.js <dir> [--preview grid.png]` — выравнивает неровный фон (виньетка/тени студийного света) на уже готовых квадратных фото каталога (перезаписывает файлы **на месте**). В отличие от баланса белого в `resize-catalog.js`/`magnity-rezh.js` (один общий коэффициент по 4 угловым точкам на весь кадр), здесь фон осветляется **локально**: маска товара по насыщенности (+ дилатация, чтобы убрать цветной ореол по краям) → усреднение фона в скользящем окне через summed-area table → на каждый пиксель свой коэффициент до целевой яркости. Нужен, когда у партии фото свет неровный по кадру (угол свет/угол тень) и общий коэффициент это не выправляет — после него один магнит может остаться сероватым/грязным на вид, даже когда все 4 угла по отдельности уже белые. Проверено: партия «Путешествие по Уралу» — разброс яркости между углами упал с ~60 до ~15 (шкала 0–255).
- `whiten-bg.js <dir> [--preview grid.png] [--band N]` — жёстче, чем `flatten-bg.js`: не выравнивает фон, а полностью заменяет его на чистый `#ffffff` (перезаписывает файлы **на месте**). Маска фона строится по насыщенности, но не наивно попиксельно — фон-кандидат (низкая насыщенность) должен ещё быть **связан по 4-связности с рамкой кадра** (BFS-заливка от границ), иначе бледные/малонасыщенные участки самого товара (белое здание, светлое небо на рисунке — не только однотонный студийный фон) посреди кадра тоже считались бы фоном и стирались в белый. Дальше — дилатация (убрать цветной ореол по краям) + мягкое перо по краю через блюр. Нужен, когда даже выровненный `flatten-bg.js` фон после ресайза в 300×300 и JPEG-сжатия всё равно даёт на сайте грязноватые/сероватые пятна по углам (мягкий градиент студийного фона при сильном уменьшении и compression добавляет видимые артефакты) — пользователь сравнивает с оригиналом на своём устройстве и видит там чистый белый, а на сайте нет. Ловушка при реализации через `sharp`: если строить маску как одноканальный `raw`-буфer и потом звать `.blur()`, sharp на выходе умолчанию расширяет её обратно в 3 канала — при наивной побайтовой индексации это даёт страйп-артефакты (полосы) вместо картинки; нужно явно `.toColourspace('b-w')` перед `.raw()` после блюра.
  - **Ловушка со связной заливкой:** если у товара на кадре крупные бледные/малонасыщенные зоны, которые доходят почти до края кадра и соприкасаются с настоящим фоном через узкие просветы (между буквами логотипа, ветками дерева и т.п.) без резкой цветной границы — BFS всё равно «протекает» через эти просветы и выедает середину рисунка (было на партии блокнотов «Я люблю Реж»: фото блокнота с бледным небом/белым зданием на обложке, снятые на сером фоне телефоном — небо и часть постройки стирались в белый вместе с фоном). Лечится флагом `--band N` — заливка от края не уходит дальше N пикселей вглубь кадра (используется реальная BFS-дистанция от границы, не DFS-порядок обхода). Для 300×300 хватает `--band 30`. Без явного `--band` (по умолчанию 0 = без ограничения) поведение как раньше — подходит для товаров, где фон однородный и не граничит с бледными деталями самого товара (например, партия магнитов «Путешествие по Уралу»).
- `otkrytki-whiten.js <srcDir> <outDir> [--sat N] [--lum N] [--core F] [--feather F]` — **замена сероватого фона на чистый белый БЕЗ обрезки и цветокоррекции самой открытки, с сохранением исходного размера/пропорций кадра** (пишет в `<outDir>`, не на месте). Отдельный инструмент под **открытки**: в отличие от `resize-catalog.js`/`magnity-rezh.js` их НЕ приводят к квадрату 300×300 и не кропят — открытка остаётся прямоугольной, как товар (это подтверждённое предпочтение пользователя: он сам готовит кадры открыток и хочет только убрать серый фон стола, ничего не срезая и не тонируя). Отличие от `whiten-bg.js`: тот строит маску фона по одной насыщенности и **градиентной** BFS — на открытках это провально «прокатывается» по гладким цветным областям (просочившись в одну точку неба открытки, заливает всё небо целиком). Здесь фон определяется **абсолютным** критерием («нейтральный как серый/белый стол»: `max−min ≤ sat` И яркость `≥ lum`), а не сравнением с соседом — цветное содержимое/рамка/бежевая бумага открытки насыщены и заливку останавливают. Плюс два предохранителя: (1) заливается только фон, **связный с краем кадра** (внутренние нейтральные детали — белые поля, серый рисунок — окружены рисунком, до края не доходят и не выбеливаются); (2) **геометрическое «ядро»** — грубый bbox открытки по плотности не-фоновых строк/столбцов, сжатый к центру на долю `core`; внутрь ядра заливка не пускается вообще, поэтому даже светлый край открытки без контрастной рамки не даёт протечки в рисунок. Рабочие параметры партии открыток «Я люблю Реж» (фото на сером столе, 300–640px): `--sat 30 --lum 108 --core 0.82 --feather 1.2`. Ловушка: при маленьком `core` (~0.5) у **очень светлых** открыток (светлое небо/бумага почти неотличимы от стола) виден прямоугольный «шов» — поля вокруг ядра выбелились, а центр остался в оригинальном тоне; лечится увеличением `core` до ~0.82 (выбеливание уходит в тонкий ободок у самого края). Единственный принципиально трудный случай — открытка со светлым небом на белом фоне без цветной рамки: идеального разделения нет, остаётся еле заметный ободок у края (приемлемо). Та же `sharp`-ловушка с `.toColourspace('b-w')` перед `.raw()` после `.blur()`, что и в `whiten-bg.js`.

Оба скрипта обрезки настраиваются константами в начале файла (`SAT`, `REL`, `MARGIN`, `TARGET`, `MAXG`, `SIZE`, `QUALITY`) — под новую партию фото с другим фоном/освещением их обычно нужно поднастроить, а не писать с нуля. При появлении новой похожей задачи (обрезать/уместить в квадрат новую партию фото каталога) — сначала смотреть сюда, а не решать вручную через графический редактор.

**Фон для карточек каталога должен быть идеально белым — это подтверждённое предпочтение пользователя, не предположение.** Прогонять `whiten-bg.js` по умолчанию как финальный шаг для любой новой партии фото товаров, а не только когда что-то выглядит явно плохо. История вопроса (партия «Путешествие по Уралу»): сначала пробовали общий баланс белого по 4 углам (`resize-catalog.js`/`magnity-rezh.js`) — после ресайза в 300×300 и JPEG-сжатия давал грязноватые/сероватые пятна по углам на сайте, хотя в оригинале фон выглядел чистым. Затем пробовали `flatten-bg.js` (локальное выравнивание яркости, не полная заливка) — стало заметно лучше, но пользователь всё равно увидел разницу между своим локальным файлом (идеально белый) и сайтом. Только полная заливка фона чистым `#ffffff` через `whiten-bg.js` дала результат, который пользователь подтвердил как «прям идеально, точно как я хотел». Поэтому `flatten-bg.js` можно считать устаревшим для этой цели — держим его в инструментарии на случай, если когда-то понадобится именно «естественный, но ровный студийный» фон, а не однородный белый, но по умолчанию для новых партий каталога нужен `whiten-bg.js`.

### Добавление новой продукции в каталог (сквозной процесс)

Пользователь скидывает исходники новой продукции (фото, любой формат — jpg/png/jfif) в `src/images/Новая продукция/` — это папка-инбокс, не в git и не в сборке gulp, обрабатывается вручную скриптами из `tools/img-tools/`. Дальше типовой процесс (проверено на партиях блокнотов и магнитов):

1. Посмотреть исходники: `sharp` metadata (формат/размеры/количество) + контактный лист превью (`montage.js` или разовый composite в scratchpad) — понять, как товар лежит в кадре.
2. Выбрать скрипт обрезки по форме товара: `resize-catalog.js`, если кадр близок к квадрату/портрету (кроп квадрата вокруг товара по насыщенности); `magnity-rezh.js`, если товар широкий/горизонтальный (плотная обрезка по объекту + вписывание contain'ом в квадрат на фоне `#f8f8f8`, без квадратного кропа). Учти: `resize-catalog.js` фильтрует только `jpg/png/webp`, `.jfif` не подхватит — либо расширить фильтр, либо использовать `magnity-rezh.js` (уже поддерживает jfif).
3. **Обязательно** прогнать с `--preview grid.png` и визуально проверить результат (обрезка, баланс белого, тени по углам) до финальной записи файлов — не пропускать этот шаг. Если фон/освещение партии отличается — поднастроить константы (`SAT/REL/MARGIN/TARGET/MAXG`) и перегенерировать превью.
4. **Прогнать `whiten-bg.js` по готовой папке** (см. раздел выше) — фон карточки должен быть идеально белым `#ffffff`, это стандартный финальный шаг для любой новой партии, а не реакция на жалобу. Снова проверить превью (`montage.js`) после этого шага.
5. Финал — 300×300 JPG, `quality` ~88 (как у остальных фото каталога), обычно 15–30 КБ на файл.
6. Разложить и переименовать по конвенции существующих партий: `src/images/img/rs/<Категория>/<kebab-слаг-товара>/<kebab-слаг>-NN.jpg` (пример: `Bloknoty/ya-lyublyu-rezh/bloknot-ya-lyublyu-rezh-01.jpg`, `Magnity/ya-lyublyu-rezh/magnit-ya-lyublyu-rezh-01.jpg`).
7. Данные карточки (название товара, цена, артикул, в какой раздел каталога и с какой стороны — в начало/конец) обычно даёт пользователь; если не дал явно — спросить, не додумывать самому.
8. Перед вставкой в `catalog-suvenir.html` — **сначала поискать grep'ом по `catalog__subtitle`**, нет ли уже раздела с таким названием/размером в этой категории. Если есть — добавлять новые карточки **в существующий** раздел (не плодить дубль с тем же заголовком — на этом уже ошибался). Разметку карточки (`<li class="catalog__item catalog-item">...`) копировать из соседней 1:1, меняя только `src`/`alt`/название/цену/артикул.
9. Обычно достаточно поправить `src/` — у пользователя запущен свой dev-сервер с watch, он сам пересоберёт `dist/`. Копировать файлы в `dist/` вручную — только если пользователь прямо говорит, что не видит изменений локально (например, watch временно не подхватил); это разовая подстраховка, не обязательный шаг.
10. Коммит/пуш/`npm run deploy` — только после того, как пользователь визуально подтвердит результат, и только по его явной просьбе (см. общее правило про риск-операции).
11. Временные превью-файлы (`--preview` grid'ы) после проверки удалить, в git не тащить.

## Дизайн и стилистика

Сайт оформлен в **светлом корпоративном стиле** на синем бренде. Палитра и брейкпоинты — в `src/styles/_variables.scss`.

- Основные цвета: `--color-primary` `#3E77FB` (фирменный синий), акцент `#6de2eb` (циан), заголовки — `--color-galaxy` `#081f5c` (тёмно-синий), текст — `#333`/`--color-dim-gray`. Градиент-акцент `linear-gradient(135deg, #3E77FB, #6de2eb)` используется в заголовках секций и подчёркиваниях.
- Хедер (`_header.scss`) — белый, футер (`_footer.scss`) — светло-голубой; оба импортируются на все страницы. Главная (`_hero`, `_work`, `_counter`, `_steps`, `_benefit`, `_contacts`) — светлые секции.
- **Логотип — две версии, не перепутать:** `logo_Lazur.svg` со слоганом в белом цвете — только под **тёмный** фон; `logo_Lazur_01.png` (синий) — под **светлый** фон. На светлых хедере/футере используется PNG.

## Самостоятельный выбор задачи

Иногда пользователь просит самому решить, над чем поработать, — без конкретного ТЗ,
просто предложить какую-то работу над проектом (не только код: правка бага, оптимизация,
новая статья/новость, доработка дизайна, любая другая осмысленная идея). Узнаётся не по
жёсткой кодовой фразе, а по смыслу просьбы — например: «предложи что-нибудь сделать»,
«над чем поработать», «выбери сам, что улучшить», «давай что-нибудь запилим», «есть идеи,
что тут можно сделать».

Услышав что-то в этом духе:

1. Свериться с [`WORKLOG.md`](WORKLOG.md) — раздел «Идеи на будущее» может уже содержать
   нереализованное предложение; если оно всё ещё актуально, предложить в первую очередь его.
2. Если готовых идей нет или ни одна не подходит — придумать самому **одну** задачу
   среднего размера (не большую), кратко предложить её пользователю (2-3 предложения, без
   немедленной реализации) и дождаться подтверждения.
3. После выполнения — дописать в `WORKLOG.md` короткую запись в разделе «Выполнено», и если
   задача была из бэклога идей — отметить её там как сделанную.
4. Идеи, которые появляются по ходу работы, но не реализуются прямо сейчас, — заносить в
   бэклог `WORKLOG.md`, а не терять. Это касается любой работы, а не только самостоятельно
   выбранных задач.

**Важно: раздел «Выполнено» — только для задач из этого сценария.** Если пользователь ставит
задачу прямым текстом («сделай новость про X», «поправь Y», «добавь Z») — это обычная
работа, запись в «Выполнено» после неё делать не нужно, даже если результат значительный
(новая статья, крупная фича и т.п.). Записывать туда — только когда идею предложил сам
ассистент по этому сценарию и пользователь её подтвердил.
